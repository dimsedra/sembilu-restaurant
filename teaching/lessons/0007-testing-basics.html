Testing: Proving It Works

Lesson 7 · How to make sure your code actually does what you think it does.

👨‍🍳 Imagine a chef who never tastes their food. They follow the recipe, plate it, and send it out. Most of the time it's fine. But sometimes the salt shaker was empty, or the oven ran hot, or they grabbed cumin instead of cinnamon. The customer is the first to find out.

That's what coding without tests is like. You write the code, it looks right, you ship it. But you only find out something is broken when a user encounters it in production.

A test is you tasting the food before it leaves the kitchen. You write a small program that calls your code, checks the result, and yells if something is wrong. You run it every time you make a change, so you catch mistakes immediately.

What does a test look like?

Here's a test for a function that adds two numbers:

function add(a: number, b: number): number {
  return a + b
}

// The test:
const result = add(2, 3)
if (result !== 5) {
  throw new Error(`Expected 5 but got ${result}`)
}

That's it. A test is just code that calls your code and checks the answer. If it throws an error, the test fails. If it doesn't throw, it passes.

Real testing frameworks (like Vitest, which we'll use) just make this pattern cleaner: 

import { describe, it, expect } from 'vitest'

describe('add', () => {
  it('adds two numbers', () => {
    expect(add(2, 3)).toBe(5)
  })
})

describe groups tests. it states what the test checks. expect asserts the result. That's the entire vocabulary.

What should we test?

You can't test everything — you'd spend all your time writing tests. The key is to test the boundary of your system — the place where the outside world meets your code.

For Sembilu's backend, that boundary is the API. A waiter's app sends an HTTP request. Our Express server responds. That's the seam where we catch mistakes.

🌐 API test example

Instead of calling a function directly, we send a fake HTTP request to our Express app:

import request from 'supertest'
import app from '../index'

it('returns all branches', async () => {
  const res = await request(app).get('/api/branches')
  expect(res.status).toBe(200)
  expect(res.body.length).toBe(4)
  expect(res.body[0].city).toBe('Tegal')
})

This test starts the Express app (without actually listening on a port), sends a GET request to /api/branches, and checks that we get 4 branches back with the right city name. If someone accidentally deletes the route or breaks the database query, this test fails.

Why test at the API level?

There are different levels of tests, like different levels of tasting:

LevelWhat it testsAnalogy
Unit test A single function in isolation Tasting a single spice before it goes in the pot
API / Integration test The whole request → response flow Tasting the finished dish before it leaves the kitchen
E2E test The full UI flow in a browser Having a customer eat the meal and tell you if it's good

API tests are the sweet spot. They test more than unit tests (they exercise routes, database queries, error handling all at once) but are faster and more reliable than E2E tests (no browser, no clicking around). One test validates the whole chain.

The rule of thumb: Test at the highest level that gives you confidence. For Sembilu's backend, that's the HTTP API — send a request, check the response, verify the database if needed. One test per endpoint (happy path + one error case) is enough to start.

What we'll use: Vitest + Supertest

  • Vitest — the test runner. It runs your tests, reports results, and integrates with Vite (which we already use for the frontend). It's fast.
  • Supertest — a tiny library that lets you make fake HTTP requests to your Express app without needing a real server port. You just pass app and it handles the rest.

Both need to be installed. After that, writing a test for a new API endpoint takes about 2 minutes.

Open the example in your project: Once we install Vitest + Supertest, we'll write a test for the GET /api/branches endpoint — using the branches we already seeded in the database.
