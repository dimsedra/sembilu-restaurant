T8 Staff Reservations: Build, Review & Refactor

Lesson 0024 · Sembilu Operating System · Informed Knowledge & Context

In this lesson, we trace the full lifecycle of T8 (Staff Reservations View & Guest Check-In) — from initial implementation through two-axis code review findings to our final refactored solution!

🚀 1. Initial Implementation Report

Our initial build created host stand endpoints in server/routes/staff-reservations.ts:

  • GET /api/staff/reservations: Joined customer details (name, phone, visit count) and filtered by branch ID and target date.
  • PATCH /api/staff/reservations/:id/status: Allowed hosts to check in guests (confirmed ➔ completed) or record cancellations (cancelled).
  • POST /api/staff/reservations: Enabled staff to record phone reservations with customer phone upserts.

🔍 2. Dual-Axis Code Review Findings

Timezone Finding Application Memory UTC Date Mismatch

Observed Code: Default date computed via Node.js new Date().toISOString().split("T")[0].

Host Stand Impact: Near midnight in Indonesia (UTC+7), Node.js computed yesterday's date in UTC, displaying yesterday's completed reservations during early morning hours!

Security Finding Inconsistent Cross-Branch POST Guard

Observed Code: POST / silently overrode branch_id for non-managers instead of returning 403 Forbidden.

Staff Impact: Inconsistent API security — non-manager waiters attempting cross-branch phone bookings didn't receive an explicit error.

Duplication Finding Copy-Pasted Manager Branch Resolution

Observed Code: Branch permission checking logic was copy-pasted across GET and POST.

Maintainability Impact: High shotgun surgery risk — changing branch security required updating multiple endpoints.

🛠️ 3. Refactored Solution & Code Walkthrough

resolveBranchAccess()
A unified security helper resolving target branch ID and enforcing 403 Forbidden consistently across GET, PATCH, and POST.
CURRENT_DATE
PostgreSQL date expression ensuring date queries match local database calendar time reliably.

Unified Branch Resolution Helper

function resolveBranchAccess(
  staff: NonNullable<AuthenticatedRequest["staff"]>,
  requestedBranchId?: unknown
): { branchId: number; isAllowed: boolean } {
  if (!requestedBranchId) {
    return { branchId: staff.branch_id, isAllowed: true }
  }

  const targetId = Number(requestedBranchId)
  if (staff.role === "manager") {
    return { branchId: targetId, isAllowed: true }
  }

  if (targetId !== staff.branch_id) {
    return { branchId: targetId, isAllowed: false }
  }

  return { branchId: staff.branch_id, isAllowed: true }
}
How this connects context to code:
  • Centralizes branch security so any unauthorized cross-branch attempt (GET, PATCH, or POST) returns HTTP 403 Forbidden cleanly!
