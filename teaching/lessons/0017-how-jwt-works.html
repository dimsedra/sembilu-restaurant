Lesson 17: How JWT (JSON Web Token) Works

Lesson 17 · Deconstructing the 3 parts of a JWT: Header, Payload, and Signature

📜 Sembilu Analogy: Imagine Manager Pak Teguh prints a staff badge for Waiter Wati. The badge states: "Name: Wati, Role: Waiter, Branch: Tegal". To prevent Wati from changing her role to "Manager" with a pen, Pak Teguh stamps it with his secret Golden Wax Seal. Whenever Wati shows her badge to the chef, the chef checks if the wax seal matches Pak Teguh's seal. That's a JWT!

1. What Does a JWT Look Like?

A JSON Web Token (JWT) is a long string separated by two dots (.) into three distinct parts:

  • Red Part: Header (Algorithm & Token Type)
  • Green Part: Payload (The actual data — staff ID, role, branch)
  • Blue Part: Signature (The secret wax seal that prevents tampering)

2. Deconstructing the 3 Parts

Part 1: The Header (Red)

Base64-URL encoded JSON that tells the server which hashing algorithm was used to sign the token (usually HS256 = HMAC with SHA-256). 

// Decodes to:
{
  "alg": "HS256",
  "typ": "JWT"
}

Part 2: The Payload (Green)

Base64-URL encoded JSON containing the Claims (the information about Wati).

⚠️ Important Security Note: Base64 encoding is NOT encryption! Anyone who gets hold of a JWT can paste it into JWT.io and read the payload. Therefore, never put sensitive secrets (like passwords or credit card numbers) in the JWT payload! 
// Decodes to:
{
  "staff_id": 1,
  "role": "waiter",
  "branch_id": 1,
  "iat": 1722340000, // Issued At (timestamp)
  "exp": 1722426400  // Expiration (timestamp)
}

Part 3: The Signature (Blue)

This is the magic part. The server takes the encoded Header, the encoded Payload, and combines them with a secret key stored on the server (JWT_SECRET) using HMAC-SHA256: 

HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  JWT_SECRET
)

3. How Verification Works (Why Tampering Fails)

Suppose Wati tries to edit her token payload in her browser from "role": "waiter" to "role": "manager". 

  Wati's Browser                           Express Server (JWT Middleware)
        │                                              │
        │  GET /api/staff/orders                       │
        │  Authorization: Bearer          │
        │ ───────────────────────────────────────────► │
        │                                              │ 1. Split token into Header, Payload, Signature
        │                                              │ 2. Re-calculate Signature using server's JWT_SECRET:
        │                                              │    expectedSig = HMAC(Header + "." + TamperedPayload, JWT_SECRET)
        │                                              │ 3. Compare expectedSig with received Signature
        │                                              │    ❌ THEY DO NOT MATCH!
        │                                              │
        │  ◄── 401 Unauthorized ("Invalid token") ─────│
Key Insight: Because Wati does not know the server's secret key (JWT_SECRET), she cannot generate a valid signature for her tampered payload. The server rejects it instantly!

4. How We Use JWT in Express (jsonwebtoken package)

In Node.js, we use the popular jsonwebtoken package:

import jwt from 'jsonwebtoken';

const JWT_SECRET = process.env.JWT_SECRET || 'super-secret-key-sembilu';

// 1. Sign (Generate token on successful login)
const token = jwt.sign(
  { staff_id: staff.id, role: staff.role, branch_id: staff.branch_id },
  JWT_SECRET,
  { expiresIn: '8h' } // Token expires after 8-hour shift
);

// 2. Verify (Middleware on protected routes)
try {
  const decodedPayload = jwt.verify(token, JWT_SECRET);
  req.staff = decodedPayload; // Attach to request object!
  next(); // Pass to route handler
} catch (err) {
  res.status(401).json({ error: 'Invalid or expired token' });
}
