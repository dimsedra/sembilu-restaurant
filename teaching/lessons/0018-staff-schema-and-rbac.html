Lesson 18: Staff Database Schema & Role Design

Lesson 18 · Single Table vs Separate Tables vs Multi-Table RBAC

🏢 Sembilu Scenario: Sembilu has three staff roles: Waiters (who view tables & mark orders served), Chefs (who view the Kitchen Display System & mark dishes cooked), and Managers (who view sales & branch reports). How should we design the database to model these employees?

1. Why Do Multiple Options Exist?

In database design, there is a constant tension between simplicity (getting things done fast with low cognitive load) and extensibility (supporting thousands of granular permissions across complex enterprise organizations).

2. Deconstructing the 3 Options

Option A: Single Table with a Role Column (Single-Table Enum)

Analogy: A single company employee directory binder. Every employee has a column called "Job Title" (Waiter, Chef, Manager). 

staff
┌────┬──────────────┬────────────────────────┬─────────────┬───────────┬───────────┐
│ id │ name         │ email                  │ password_h  │ role      │ branch_id │
├────┼──────────────┼────────────────────────┼─────────────┼───────────┼───────────┤
│ 1  │ Wati         │ wati@sembilu.com       │ $2a$10$...  │ waiter    │ 1 (Tegal) │
│ 2  │ Budi         │ budi@sembilu.com       │ $2a$10$...  │ chef      │ 1 (Tegal) │
│ 3  │ Teguh        │ teguh@sembilu.com      │ $2a$10$...  │ manager   │ 1 (Tegal) │
└────┴──────────────┴────────────────────────┴─────────────┴───────────┴───────────┘
  • Why it exists: To solve authentication & authorization with the smallest, deepest model possible. All employees log in the same way (email + password).
  • Pros:
    • 1 SQL Query for Login: SELECT * FROM staff WHERE email = ?
    • Matches JWT 1:1: The payload `{ staff_id: 1, role: 'waiter', branch_id: 1 }` directly reflects DB columns.
    • Zero duplication: All staff share login logic, password hashing, and branch foreign keys.
  • Cons: If a manager needs 20 special fields (like `bank_account_number`, `annual_salary`) that waiters don't have, those columns will be `NULL` for waiters.
  • Best Use Case: Small to medium applications, restaurant OSs, and systems where staff roles are fixed and well-defined.

Option B: Separate Tables per Role (`waiters`, `chefs`, `managers`)

Analogy: 3 separate binder notebooks in the office. One binder labeled "Waiters", one labeled "Chefs", one labeled "Managers". 

waiters                 chefs                   managers
┌────┬──────┬─────────┐ ┌────┬──────┬─────────┐ ┌────┬──────┬──────────────┐
│ id │ name │ email   │ │ id │ name │ email   │ │ id │ name │ salary       │
└────┴──────┴─────────┘ └────┴──────┴─────────┘ └────┴──────┴──────────────┘
  • Why it exists: Developers sometimes create this when different roles have completely different attributes and business logic.
  • Pros: No `NULL` columns. `managers` can have salary columns without affecting `waiters`.
  • Cons:
    • Nightmare Login Logic: When someone submits an email to POST /api/staff/login, which table do you search? You have to search `waiters`, then `chefs`, then `managers`, or run a slow `UNION` query.
    • Duplicated code & Foreign Keys: Every order item needs FKs pointing to 3 different tables.
  • Best Use Case: Almost NEVER for authentication. Only useful when entities are fundamentally different domain concepts (e.g., `customers` vs `staff`).

Option C: Multi-Table RBAC (Role-Based Access Control)

Analogy: A high-security government building. Users have badges, badges have roles, and roles have granular permission slips (e.g., `orders:read`, `menu:write`, `reports:export`). 

users               user_roles            roles                 role_permissions        permissions
┌──────────┐        ┌─────────┬─────────┐ ┌─────────┬─────────┐ ┌─────────┬───────────┐ ┌──────────────┐
│ id       │───────►│ user_id │ role_id ││ id      │ name    ││ role_id │ perm_id   ││ id           │
│ email    │        └─────────┴─────────┘ ├─────────┼─────────┤ └─────────┴───────────┘ ├──────────────┤
│ pass_hash│                              │ 1       │ Waiter  │◄───────────────────────│ orders:read  │
└──────────┘                              │ 2       │ Chef    │                         │ kitchen:cook │
                                          └─────────┴─────────┘                         └──────────────┘
  • Why it exists: Created for enterprise SaaS products (like Salesforce, AWS, or GitHub) where admins can invent custom roles with fine-grained permission checkboxes.
  • Pros:
    • Unlimited Flexibility: A user can have multiple roles (e.g., Chef + Manager).
    • Dynamic Permissions: Admins can toggle individual permission checkboxes in a UI.
  • Cons:
    • High Complexity: Requires 5 database tables and multi-table `JOIN` queries just to check if a user can click a button.
    • High Cognitive Load: Overkill for apps with fixed, static roles.
  • Best Use Case: Enterprise SaaS, cloud portals, and multi-tenant applications with customizable admin panels.

3. Summary Comparison for Sembilu

Pattern Tables Needed Login Query Speed Cognitive Load Fit for Sembilu
Option A: Single Table (role) 1 table (`staff`) ⚡ Blazing (1 lookup) 🟢 Very Low 🌟 Perfect fit
Option B: Separate Tables 3+ tables 🐢 Slow (3 lookups/UNION) 🔴 Very High ❌ Anti-pattern
Option C: Enterprise RBAC 5 tables 🟡 Medium (4 JOINs) 🟡 High ⚠️ Over-engineered

4. Summary Recommendation

Option A (Single staff table with role column) is the gold standard choice for Sembilu:
It gives us an elegant, fast, 1-table design that matches our JWT token payload { staff_id, role, branch_id } directly, making Express route middleware simple to write and easy to understand!
