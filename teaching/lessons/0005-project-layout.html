Project Layout: Where Does Everything Go?

Lesson 5 · Why there are different ways to organize a frontend + backend project, and which one Sembilu needs.

🏗️ Imagine you're building a house. Do you put the kitchen, bedroom, and workshop all in one big room? Do you build separate buildings for each? Or do you build a house with clearly separated rooms, all under one roof?

That's what "project layout" is about — how you arrange the files for your frontend (React) and backend (Express) when they live in the same Git repository. The right choice depends on what kind of project you're building.

First, understand the two sides

Sembilu now has two "halves":

Frontend (src/)Backend (new)
What it doesUI — what customers and staff see in the browserAPI — handles requests, talks to the database, sends real-time updates
Runs onThe user's browserA server (your computer, for now)
DependenciesReact, react-router, TailwindExpress, knex, pg, socket.io
It needs to…Look beautiful, feel fastStore data, enforce rules, push updates

These two halves are different worlds — different concerns, different dependencies, different runtime. But they're part of the same product, so they should live in the same repository (same Git repo).

The question is: how do you arrange them inside that repo?

Option A: Two folders, one package.json

sembilu-restaurant/ ├── src/ ← React frontend (stays as-is) │ ├── components/ │ ├── data.ts │ └── App.tsx ├── server/ ← Express backend │ ├── routes/ │ ├── migrations/ │ ├── knexfile.js │ └── index.js ├── package.json ← ONE file listing ALL dependencies ├── vite.config.ts └── index.html

Why this exists: For small-to-medium projects where one person or a small team builds everything. It's the simplest setup — you run npm install once, you have one package.json, you understand the whole project from one file.

ProsCons
✅ One npm install — everything in one place❌ Frontend and backend deps mixed together in package.json
✅ Simple to understand — just two folders❌ As it grows, package.json becomes long and messy
✅ Easy to run both with one command (concurrently)❌ Harder to swap out a piece later (can't easily replace just the backend)
✅ No monorepo tooling to learn❌ No strict boundary — frontend code could import backend code by accident

Used by: Small teams, prototypes, personal projects, hackathons.

Option B: Monorepo with workspaces

sembilu-restaurant/ ├── packages/ │ ├── client/ ← React frontend │ │ ├── package.json ← its own deps (React, etc.) │ │ ├── vite.config.ts │ │ └── src/ │ └── server/ ← Express backend │ ├── package.json ← its own deps (Express, knex, etc.) │ └── src/ ├── shared/ ← Optional: types used by both │ └── types.ts ├── package.json ← root — just workspace config

Why this exists: For larger projects where the frontend and backend are built by different teams, or where you want them to be truly independent but still in the same repo. Tools like npm workspaces, pnpm workspaces, and Turborepo manage this.

ProsCons
✅ Clean separation — each half has its own dependencies❌ Need to learn monorepo tooling (workspaces, hoisting, etc.)
✅ Can have a shared/ package for types used by both❌ npm install is slower, more complex
✅ Scales to many packages (add a mobile app? just another package)❌ Overkill for a two-person project
✅ Each package can have its own build/dev/test commands❌ "Where's the bug?" — harder to debug across packages

Used by: Large teams (Spotify, Google), open-source projects, companies with multiple products sharing code.

Option C: Flat everything in src/

sembilu-restaurant/ ├── src/ │ ├── client/ ← React: components, pages, styles │ ├── server/ ← Express: routes, middleware, migrations │ └── shared/ ← Types both sides use └── package.json

Why this exists: When you want maximum simplicity and don't mind the two sides living in the same folder. Some frameworks (like Next.js) actually do this — they put API routes inside the same folder as pages.

ProsCons
✅ Everything is right there — no folder nesting❌ Gets messy fast — hard to tell what belongs where
✅ Shared types are trivially close❌ No clear boundary — easy to accidentally mix concerns
✅ Single build/dev setup❌ Doesn't scale — at some point you'll want to separate them

Used by: Very small projects, quick prototypes, tutorials.

Which one for Sembilu?

Let's think about what Sembilu actually needs:

  1. One developer (you) building both frontend and backend — no team coordination needed
  2. You're learning — you don't want to also learn monorepo tooling on top of everything else
  3. The frontend is already built — moving everything to a monorepo means restructuring existing files
  4. You need to run both together — one command should start the Vite dev server + the Express server

Now check each option against these needs:

Option A (two folders)Option B (monorepo)Option C (flat)
Learning curveNoneMediumNone
Setup timeMinutesHoursMinutes
Keeps existing src/ intact?✅ Yes❌ Need to move it✅ Yes
Scales well?Good enoughBestPoor
Shared typesManual importBuilt-inTrivial
Industry common?Common for small projectsCommon for big teamsRare for real projects
Why Option A wins for Sembilu: Monorepo tooling adds a layer you'd need to learn and debug — on top of Express, knex, PostgreSQL, WebSocket, and everything else. Option A adds zero complexity. You just create a server/ folder and start writing code. If the project grows huge (unlikely for a restaurant system), you can migrate to a monorepo later. But by then you'll understand why you need it, instead of learning it upfront.
