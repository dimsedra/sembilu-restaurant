T2 Recap: Sambals API

Lesson 12 · The same pattern as T1, just simpler — prove the rhythm works.

👩‍🍳 Wati learned about the sambals. Before T2, she had the 9 sambals memorized from a piece of paper. After T2, she has them written in her book. Same as the dishes, but simpler — sambals don't belong to a specific branch. They're universal.

T2 followed the exact same vertical slice pattern as T1. The repetition is intentional — you're building muscle memory for the workflow: 

  Write test   →   Write migration   →   Write route   →   Update frontend
  (fails)          (creates table)       (passes test)      (fetches from API)

Layer 1: The Test

File: server/routes/sambals.test.ts

it("returns all 9 sambals", async () => {
  const res = await request(app).get("/api/sambals")
  expect(res.status).toBe(200)
  expect(res.body.length).toBe(9)       // ← must be exactly 9
  expect(res.body[0]).toHaveProperty("name")
  expect(res.body[0]).toHaveProperty("heat")
  expect(res.body[0]).toHaveProperty("note")
})

it("each sambal has a valid heat level", async () => {
  const res = await request(app).get("/api/sambals")
  res.body.forEach((s) => {
    expect(s.heat).toBeGreaterThanOrEqual(1)  // ← minimum pedas
    expect(s.heat).toBeLessThanOrEqual(3)     // ← maximum pedas
  })
})

The first test checks the count and structure. The second test is more interesting — it iterates over every sambal and validates the heat level is within 1–3. If someone accidentally inserts a sambal with heat: 5, this test catches it.

Layer 2: The Migration

File: server/migrations/20260730-create-sambals.ts

await knex.schema.createTable("sambals", (table) => {
  table.increments("id")
  table.string("aksara_no").notNullable()  // ← Javanese numeral for display
  table.string("name").notNullable()
  table.integer("heat").notNullable()       // ← 1–3
  table.text("note").notNullable()
  table.timestamps(true, true)
})

Key difference from dishes: No branch_id foreign key. Sambals are universal — every Sembilu branch serves all 9. No FK needed.

The seed inserts all 9 sambals in order, matching data.ts exactly.

Layer 3: The Route

File: server/routes/sambals.ts

router.get("/", async (_req, res) => {
  const sambals = await db("sambals").orderBy("id")
  res.json(sambals)
})

Simpler than dishes — no filter, no /:id. Just one endpoint that returns all sambals ordered by their ID (which matches the aksara order: ꧑ to ꧙).

Then registered in server/index.ts:

app.use("/api/sambals", sambalsRouter)

Layer 4: The Frontend

File: src/components/Sambal.tsx

The refactor was almost identical to Menu.tsx:

// Before:
import { sambals } from "@/data"   // ← hardcoded

// After:
const [sambals, setSambals] = useState([])
useEffect(() => {
  fetch("/api/sambals")
    .then(r => r.json())
    .then(setSambals)
}, [])

The component structure stayed exactly the same — same heat indicators, same cards, same layout. Only the data source changed.

The pattern is established

After T1 and T2, the workflow is now predictable:

  1. Test first — define what success looks like
  2. Migration — create the table matching the data shape
  3. Route — wire up the endpoint using knex
  4. Frontend — swap hardcoded import for fetch
  5. Verify — npm test (all pass) + npm run build

Every ticket from here follows this same rhythm. T3 (Reservations) will be the first to break the pattern — it needs a POST endpoint with validation, not just GET. But the structure is the same.

Try it: npm run dev and open the homepage — scroll to the Sambal section. The 9 sambals now come from the database. Open DevTools → Network to see the GET /api/sambals request.

What's next? T3 is the first POST endpoint — it takes data from the user instead of just sending data to them. That's a new concept.
