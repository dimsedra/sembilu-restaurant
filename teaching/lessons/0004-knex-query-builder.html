Knex: Queries Like Sentences

Lesson 4 · A query builder is SQL written in JavaScript, one method at a time.

📝 Imagine writing a sentence by snapping LEGO blocks together. Each block is one word: "SELECT" block, "FROM" block, "WHERE" block. You snap them together in a chain, and Knex assembles the full SQL sentence for you at the end.

What is a query builder?

A query builder is not an ORM. An ORM (like Prisma) tries to hide SQL from you — you work with "objects" and it figures out the SQL. A query builder does the opposite: it shows you the SQL, just in a more convenient form.

Raw SQL:

SELECT * FROM orders WHERE branch_id = 1 AND status = 'pending'

Knex:

knex('orders')
  .where({ branch_id: 1, status: 'pending' })
  .select('*')

See? The same structure. You just write it as a chain of JavaScript methods instead of a string.

Why knex over Drizzle?

Both are query builders. The difference is in how they feel when you write them:

Knex

knex('orders')
  .join('branches', 'orders.branch_id', 'branches.id')
  .where('orders.status', 'pending')
  .select(
    'orders.id',
    'branches.city',
    'orders.table_number'
  )

The SQL sentence is visible in the chain.

Drizzle

db
  .select({ id: orders.id, city: branches.city, table: orders.tableNumber })
  .from(orders)
  .leftJoin(branches, eq(orders.branchId, branches.id))
  .where(eq(orders.status, 'pending'))

More TypeScript magic, less obviously SQL.

knex: You write .where('status', 'pending') and it reads like "WHERE status = 'pending'". The SQL is right there.

Drizzle: You import eq and call eq(orders.status, 'pending'). It's valid TypeScript but requires you to know what eq does. More abstraction between you and the actual query.

The deciding factor: Since you chose Express specifically to learn how things work, knex gives you a clearer view of the SQL. With Drizzle you'd be learning Drizzle's TypeScript patterns plus SQL. With knex, you mostly just learn SQL with JavaScript syntax.

What you'll actually write

Here's what a typical day with knex looks like, using Sembilu's data:

Inserting a new branch

await knex('branches').insert({
  city: 'Tegal',
  address: 'Jl. Jenderal Sudirman No. 17, Tegal',
  hours: 'Setiap hari · 10.00 – 22.00',
  open: true,
})

Querying all dishes at a branch

const dishes = await knex('dishes')
  .join('branches', 'dishes.branch_id', 'branches.id')
  .where('branches.city', 'Tegal')
  .select('dishes.name', 'dishes.price')

This generates SQL like: SELECT dishes.name, dishes.price FROM dishes JOIN branches ON dishes.branch_id = branches.id WHERE branches.city = 'Tegal'

Updating an order status (kitchen marks "done")

await knex('order_items')
  .where({ id: 42 })
  .update({ status: 'done' })

Counting tonight's pending orders

const count = await knex('orders')
  .where({ branch_id: 1, status: 'pending' })
  .count('id as total')

// count = [{ total: 5 }]

Migrations: version control for your database

Knex has a built-in migration system. A migration is a file that describes a change to your database schema — creating a table, adding a column, etc. They run in order and can be rolled back.

You create a migration with:

npx knex migrate:make create_branches

It generates a file like migrations/20240729_create_branches.js:

exports.up = function (knex) {
  return knex.schema.createTable('branches', (table) => {
    table.increments('id')           // auto-incrementing primary key
    table.string('city').notNullable()
    table.text('address')
    table.string('hours')
    table.boolean('open').defaultTo(true)
  })
}

exports.down = function (knex) {
  return knex.schema.dropTable('branches')
}

Why this matters: Every time you change the database, you write a migration. Your teammates (or future you) run npx knex migrate:latest and their database is exactly in sync. No "oh I forgot, I also added a column manually last week."

Convex vs Knex — the difference

Since you've used Convex before, here's the key difference:

ConvexKnex
Runs where?On Convex's cloud serversIn your Node.js process
DatabaseConvex's own (proprietary)PostgreSQL (standard SQL)
QueriesJavaScript functions that run on the serverChained methods → SQL → PostgreSQL
MigrationsSchema is defined by your dataExplicit migration files you write
Type safetyBuilt-in (Convex generates types)You write types yourself (or use knex TypeScript types)

The biggest practical difference: Convex handles everything (database, server, sync) as one product. Knex is just the query builder — you need to set up Express as the server, PostgreSQL as the database, and a WebSocket library for real-time yourself. More files, more wiring, but you understand every piece.
