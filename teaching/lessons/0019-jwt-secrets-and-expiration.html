Lesson 19: JWT Secrets & Token Expiration

Lesson 19 · Understanding process.env, Hardcoded Secrets, and Refresh Tokens

🔑 Sembilu Analogy: The JWT_SECRET is Pak Teguh's private stamp tool. If a hacker gets hold of the stamp tool, they can forge valid staff badges for anyone! Meanwhile, the Expiration Date is the stamp on Wati's badge saying "Valid for Shift #1 (8 Hours Only)". If Wati drops her badge on the floor after her shift, a stranger cannot use it tomorrow.

1. Why Do Secret Management Options Exist?

In software development, security bugs frequently happen not because the math is broken, but because developers accidentally leak secrets into source code repositories or issue tokens that live forever.

2. Deconstructing the 3 Options

Option A: Environment Variable (`JWT_SECRET`) + Dev Fallback + Shift Expiry

Analogy: Pak Teguh keeps the master stamp tool inside a physical safe (`.env`). In the test kitchen, he leaves a dummy rubber stamp (`'sembilu-dev-secret'`). Badges expire at the end of every 8-hour shift. 

// In server/routes/staff.ts
const JWT_SECRET = process.env.JWT_SECRET || 'sembilu-dev-secret';

// Sign token with 8-hour expiration
const token = jwt.sign(
  { staff_id: staff.id, role: staff.role, branch_id: staff.branch_id },
  JWT_SECRET,
  { expiresIn: '8h' }
);
  • Why it exists: To separate configuration/secrets from source code (Principle #3 of the 12-Factor App methodology). `.env` files are added to `.gitignore` so secrets are never pushed to GitHub.
  • Why 8 Hours? 8 hours matches a standard staff shift. If Wati logs in at 09:00 AM, her token works seamlessly during her shift and naturally expires at 05:00 PM.
  • Pros: Secure, zero chance of leaking production keys into Git, clean dev fallback for running tests, zero database overhead.
  • Cons: If Wati gets fired mid-shift, her token still works for the remainder of the 8 hours unless a token blacklist is checked.

Option B: Hardcoded Secret String in Source Code

Analogy: Writing the vault password in permanent marker directly on the restaurant's front window. 

// ❌ DANGEROUS ANTI-PATTERN
const JWT_SECRET = 'my-super-secret-12345'; // Hardcoded directly in code
  • Why it exists: Developers do this during quick 5-minute tutorials or prototypes because creating a `.env` file feels like extra effort.
  • Why it's a huge trap: Automated bots scan public GitHub repositories 24/7. The moment code with hardcoded secrets is pushed, bots extract the key within seconds and breach production systems.
  • Pros: 0 setup steps in 30-second toy scripts.
  • Cons: Critical security flaw. Never use in production or real projects.

Option C: Refresh Tokens (15-Min Access + Long Refresh Token in DB)

Analogy: Wati receives a 15-minute temporary wristband (Access Token) + a High-Security Smartcard (Refresh Token). Every 15 minutes, her phone taps the smartcard against the manager's computer to get a new 15-minute wristband. 

1. LOGIN: Server returns Access Token (15 mins) + Refresh Token (7 days, saved in DB).
2. API CALLS: Client uses 15-min Access Token.
3. EXPIRATION: After 15 mins, Access Token expires.
4. REFRESH: Client calls `POST /api/staff/refresh` with Refresh Token.
   Server checks DB: Is refresh token revoked? If active, issue new 15-min Access Token!
  • Why it exists: Solves the problem of stolen tokens. If a hacker steals Wati's Access Token, it only works for 15 minutes max. And if Wati is fired, the manager deletes her Refresh Token from the DB, blocking her from getting new access tokens.
  • Pros: Maximum security for high-risk applications (financial apps, banking portals, social networks).
  • Cons: High architectural complexity — requires writing refresh token DB tables, rotation logic, token reuse detection, and client-side silent refresh interceptors.

3. Comparison Matrix for Sembilu

Criteria Option A: env + 8h Shift Option B: Hardcoded Secret Option C: Refresh Tokens
Git Security 🟢 Safe (Secrets in `.env`) 🔴 Severe Risk (Leaked to Git) 🟢 Safe (Secrets in `.env`)
Window of Exposure 🟡 8 Hours (Shift length) 🔴 Infinite (No expiry) 🟢 15 Minutes
Code Complexity 🟢 Low & Clean 🟢 Low (Trivial) 🔴 High (2 tokens + DB table)
Fit for Restaurant OS 🌟 Perfect fit for shift work ❌ Anti-pattern ⚠️ Over-engineered for local OS

4. Summary Recommendation

Option A is the ideal choice for Sembilu:
It teaches 12-Factor App secret management via process.env.JWT_SECRET, protects against Git leaks, and models real-world 8-hour staff shifts without drowning us in refresh token rotation overhead.
