1. The 3 Core Pillars of Staff Authentication

Pillar 1 Password Hashing with bcryptjs

We never store plain text passwords (e.g. "password123") in the database. Instead, during account creation or seeding, we run: 

const passwordHash = await bcrypt.hash("password123", 10);
// Result: $2a$10$wN8Gk5r.4Y9lH7z... (60-char one-way hash)

When a staff member logs in via POST /api/staff/login, we retrieve their hash and verify: 

const isMatch = await bcrypt.compare(password, staff.password_hash);
if (!isMatch) { return res.status(401).json({ error: "Invalid credentials" }); }

Pillar 2 Stateless JWT Tokens & Expiration

When password verification succeeds, the server issues a signed JSON Web Token (JWT) valid for 8 hours (a standard restaurant shift): 

const payload: StaffPayload = {
  staff_id: staff.id,
  role: staff.role,     // "waiter" | "chef" | "manager"
  branch_id: staff.branch_id
};

const token = jwt.sign(payload, getJwtSecret(), { expiresIn: "8h" });

Because all staff context (ID, role, branch) is cryptographically signed inside the token, downstream routes can read req.staff with 0 database lookup overhead per request!

Pillar 3 Express Auth Middleware (requireStaffAuth)

To protect internal routes like GET /api/staff/me or kitchen orders, our middleware intercepts the request: 

export function requireStaffAuth(req: AuthenticatedRequest, res: Response, next: NextFunction) {
  const authHeader = req.headers.authorization;
  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    return res.status(401).json({ error: "Authentication required. Missing Bearer token." });
  }

  const token = authHeader.split(" ")[1];
  try {
    const decoded = jwt.verify(token, getJwtSecret());
    if (!isValidStaffPayload(decoded)) {
      return res.status(401).json({ error: "Invalid token payload structure." });
    }
    req.staff = decoded; // Attach payload to Express request!
    next();
  } catch (err) {
    return res.status(401).json({ error: "Invalid or expired token." });
  }
}

2. Key Architectural Refactorings Learned

❌ Before (Code Smell)

DML inside DDL Migration: Hardcoded test users inserted inside createTable migration file.

Unsafe Type Assertion: decoded as StaffPayload forced TypeScript to trust untrusted token data blindly.

Hardcoded Dev Secret Fallback: Fallback secret available everywhere without production environment checks.

✅ After (Clean Architecture)

Pure DDL Migration + Knex Seeds: 20260730-create-staff.ts defines table structure only; test data moved to server/seeds/01_staff.ts.

Runtime Type Guard: isValidStaffPayload(decoded) checks positive integer IDs and validates `role` against VALID_STAFF_ROLES.

12-Factor Secret Enforcement: getJwtSecret() strictly throws in production if JWT_SECRET environment variable is missing.

3. Check Your Understanding

Question 1: Why did we move knex("staff").insert(...) out of the migration file and into server/seeds/01_staff.ts?

Answer: To keep migrations strictly DDL (Data Definition Language). DDL creates table schemas. DML (Data Manipulation Language) populates data. Mixing data into migrations causes foreign key failures when setting up fresh databases.

Question 2: What is the difference between decoded as StaffPayload and isValidStaffPayload(decoded)?

Answer: as StaffPayload is a static compile-time assertion that tells TypeScript to trust you without checking. isValidStaffPayload(decoded) executes real code at runtime to verify `staff_id`, `role`, and `branch_id` before allowing the request through!
