T3 Recap: Customers + Reservations

Lesson 13 · The first POST endpoint — sending data TO the server, not just reading.

👩‍🍳 Wati now has a reservation book. Before T3, when you said "I want to book a table for Saturday," Wati would nod and hope she remembers. After T3, she pulls out her reservation book, writes your name and phone number, and you're in the system. Next time you call, she recognizes your number instantly.

T1 and T2 were all about reading data — GET requests. The server sends data to the browser. T3 is the first time we write data — a POST request. The browser sends data to the server, the server saves it to the database.

Two tables, not one

T3 creates two database tables instead of one — because a reservation links a customer to a time and place. 

customers                          reservations
┌─────────────────────┐            ┌─────────────────────────┐
│ id (PK)             │◄──────────│ customer_id (FK)        │
│ name                 │            │ branch_id (FK)          │
│ phone (UNIQUE)       │            │ date                    │
│ visit_count          │            │ time                    │
│ notes                │            │ party_size              │
│ created_at           │            │ status                  │
└─────────────────────┘            └─────────────────────────┘

Why two tables? Because one customer can make many reservations over time. If we put name + phone inside the reservations table, we'd repeat that data every time Budi books a table. By separating them, Budi's data lives in one place and each reservation just points to his customer ID.

The "find or create" pattern

The key logic in the POST endpoint:

// Step 1: Is this phone number already in our system?
let customer = await db("customers").where("phone", phone).first()

if (customer) {
  // Returning customer — increment their visit count
  await db("customers").where("id", customer.id)
    .increment("visit_count", 1)
  customer = await db("customers").where("id", customer.id).first()
} else {
  // New customer — create a record
  await db("customers").insert({ name, phone, visit_count: 1 })
  customer = await db("customers").where("phone", phone).first()
}

// Step 2: Create the reservation linked to this customer
await db("reservations").insert({
  customer_id: customer.id,
  branch_id, date, time, party_size
})

This pattern — find or create — is everywhere in web apps. Login? "Find or create user by email." Add to cart? "Find or create cart by customer ID."

The test difference

In T1 and T2, tests were simple — just read data and check. In T3, each test writes data, so we need to clean up between tests: 

afterEach(async () => {
  await db("reservations").del()  // delete reservations first
  await db("customers").del()      // then delete customers
})

Order matters here — you can't delete customers before reservations because the foreign key would complain: "Can't delete customer #7, reservation #42 still references them!" This is referential integrity in action.

The bug we found (and fixed)

During the code review, we found a problem:

Before fix: branchIndex = cities.indexOf(branch) + 1 — this computed the branch ID by finding the city's position in an array and adding 1. If the array order changed (e.g., "Jakarta" moved before "Slawi"), a Jakarta reservation would silently become a Slawi reservation.

After fix: branchIdMap: { Tegal: 1, Slawi: 2, Semarang: 3, Jakarta: 4 } — explicit mapping, independent of array order. Can't break.

This is a classic real-world lesson: never derive an ID from an array position. Array order can change. An explicit map or a database lookup cannot.

What's next (T4)

T4 (Orders API) will be another POST endpoint, but more complex — it needs to validate that the ordered dishes actually belong to the chosen branch, handle multiple line items, and calculate totals. The find-or-create pattern from T3 will serve as a foundation.

Try it: Go to the homepage, scroll to Reservasi, fill in your details and submit. Then check the database: docker exec sembilu-db psql -U postgres -d sembilu -c "SELECT * FROM customers"

Key takeaway: POST = sending data. Find-or-create = check first, then decide: update existing or create new. Two tables instead of one when data has a "one-to-many" relationship (one customer → many reservations).

Confused? Ask. The find-or-create pattern is everywhere and worth understanding.
