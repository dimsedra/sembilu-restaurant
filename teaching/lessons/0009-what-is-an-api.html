What is an API?

Lesson 9 · The translator between your frontend and your database.

🗣️ You're at a Sembilu table. You speak Indonesian. The chef speaks Javanese. You can't just walk into the kitchen and start shouting. You need the waiter to translate: you say "I want Ikan Bakar," the waiter tells the chef in the language they understand, then brings back your food.

That waiter is the API. It's the middleman that takes a request from one side (your React app), translates it into something the other side (the database) can understand, and brings the result back.

API vs API Key — the confusion

You mentioned you thought API was something like an "API Key." That's a very common confusion. Let's separate them:

Web APIAPI Key
The waiter itself — the system that handles requestsA password you show to prove you're allowed to use the waiter
Example: Express API — the routes in our server/ folderExample: sk-abc123 — a secret string you send in the header
"I built an API for Sembilu" = I created the waiter"I need an API key for OpenAI" = I need a password to use their waiter

An API Key is just ONE tiny piece of security that some APIs use. It's like a VIP badge. But the API itself is the whole waiter system — the menus, the ordering process, the communication.

The API sits in the middle. It's the only thing the frontend talks to. The frontend NEVER talks to the database directly. Why?

  • Security — if the browser talked to the database directly, anyone could open DevTools and delete all your data. The API controls what's allowed.
  • Logic — the API enforces rules. "Can you order a dish that's only available in Jakarta from the Tegal branch?" The API checks and says no.
  • Formatting — the database returns raw rows. The API shapes them into clean JSON that the frontend can use directly.

Concrete example: Placing an order

When a waiter submits an order, here's everything the API does:

Step 1: Receive the request
POST /api/orders
{
  "branch_id": 1,
  "table_number": 5,
  "items": [
    { "dish_id": 1, "quantity": 2 },
    { "dish_id": 3, "quantity": 1 }
  ]
}

Step 2: Validate
- Does branch 1 exist? ✓
- Do dish 1 and 3 belong to branch 1? ✓
- Are quantities positive? ✓

Step 3: Write to database
INSERT INTO orders (branch_id, table_number, status)
VALUES (1, 5, 'pending')
RETURNING id
  → order_id = 42

INSERT INTO order_items (order_id, dish_id, quantity, status)
VALUES (42, 1, 2, 'pending'), (42, 3, 1, 'pending')

Step 4: Notify the kitchen (via WebSocket)
"New order at table 5!"

Step 5: Send response back
{
  "id": 42,
  "status": "pending",
  "items": [...]
}

Without the API, the waiter would have to open the database directly and type raw SQL. With the API, they just click "Send" and the API handles the rest.

So back to the tickets

When I say "T1 — Dishes API", I mean: build the waiter that handles requests about dishes. When the frontend (or a test) says GET /api/dishes, the API responds with the menu. When it says GET /api/dishes/3, the API responds with just Gurame Asam Manis.

Each ticket builds one tiny waiter for one specific type of request. By the end of 9 tickets, we have a full waitstaff.

Try it now: If your server is running (npm run dev:server), open http://localhost:3001/api/health in your browser. You just used the API. The { "status": "ok" } is the API talking back to you.
