Lesson 16: Staff Authentication — How Servers Remember Who You Are

Lesson 16 · Understanding JWT Bearer Headers, Cookies, and Server Sessions from zero

🏷️ Sembilu Analogy: When Waiter Wati arrives for her shift at SEMBILU Tegal, she logs in once. How does the server know it's still Wati 5 minutes later when she clicks "Mark Order as Cooking"? HTTP is stateless (it forgets you between every request). We need a mechanism to prove Wati's identity on every single request.

1. The Fundamental Problem: HTTP Has Memory Loss

Every HTTP request is completely independent. When Wati's browser asks GET /api/staff/orders, Express has zero memory that 3 seconds ago Wati sent her password to POST /api/staff/login.

To solve this, after logging in, the server gives Wati a proof of identity. Wati's browser includes this proof on every single future request.

2. The Three Options Explained

Option A: Stateless JWT in Authorization Header (Bearer Token)

Analogy: The manager prints a tamper-proof Laminated Wristband (JWT) and hands it to Wati. Wati holds up her wristband whenever she enters the kitchen or asks for orders. 

1. LOGIN: Wati posts email + password ──► Server checks DB ──► Generates JWT wristband
2. SERVER RESPONSE: Returns { token: "eyJhbGciOi..." }
3. FUTURE REQUESTS: Browser attached header on every call:
   Authorization: Bearer eyJhbGciOi...
4. VERIFICATION: Server inspects token signature using a secret key.
   No database query needed! Token says: "I am Wati, Role: Waiter, Branch: Tegal".
  • What is a JWT (JSON Web Token)? A digitally signed string containing JSON data (like staff ID, role, and branch). Because it is signed with a secret key on the server, nobody can tamper with it (e.g. Wati can't change her role to "Manager").
  • Pros: Stateless & Fast. The server doesn't have to look up Wati in the database on every single API request. Works perfectly across different domains/ports and in REST APIs.
  • Cons: Stored in frontend JS memory/localStorage (vulnerable to XSS script injection if malicious code runs). Cannot be easily invalidated until it expires unless a blacklist is used.

Option B: HTTP-Only Cookie containing a JWT

Analogy: The manager puts Wati's wristband in a Locked Metal Box (HTTP-Only Cookie). Wati carries the box. Every time she talks to the kitchen, the browser automatically shows the box. JavaScript running in Wati's phone cannot touch or inspect what's inside the box. 

1. LOGIN: Server returns HTTP Response Header:
   Set-Cookie: token=eyJhbGci...; HttpOnly; SameSite=Strict
2. FUTURE REQUESTS: Browser automatically includes the cookie on every request:
   Cookie: token=eyJhbGci...
3. VERIFICATION: Server reads token from cookie and verifies signature.
  • Pros: Highly Secure against XSS. JavaScript cannot read HTTP-Only cookies, preventing malicious scripts from stealing the token.
  • Cons: Slightly more complex setup (requires CORS credentials configuration if frontend and backend run on different ports in dev, e.g. 5173 vs 3000), and requires protection against CSRF (Cross-Site Request Forgery).

Option C: Stateful Server Session (Database / Redis)

Analogy: Every time Wati makes a request, she says "I am Ticket #9482". The manager opens a giant physical ledger book in the office (Database/Redis), scans down line #9482, and checks if Wati is logged in and what her permissions are. 

1. LOGIN: Server creates a row in `sessions` table: { id: "sess_9482", staff_id: 1 }
2. SERVER RESPONSE: Sends session ID cookie `sess_9482`.
3. FUTURE REQUESTS: Browser sends cookie `sess_9482`.
4. VERIFICATION: Server runs a SQL query: SELECT * FROM sessions WHERE id = 'sess_9482'.
  • Pros: Easy to instantly revoke access (just delete the row in the database).
  • Cons: Database Overhead. Every single API request (getting orders, changing table status, checking reservations) forces a database lookup just to check who is logged in.

3. Comparison Matrix for Sembilu

Criteria Option A: Bearer JWT Header Option B: HTTP-Only Cookie Option C: Server Session

4. Summary Recommendation

Recommendation for Sembilu (Option A — Bearer JWT):
Issue #5 explicitly calls for: POST /api/staff/login returning a JWT token.
Using Option A (Bearer Header) is the purest, most educational way to learn how modern REST APIs and SPAs communicate. The server signs a token with { staff_id, role, branch_id }, and our Express auth middleware simply inspects req.headers.authorization to grant or deny access!
