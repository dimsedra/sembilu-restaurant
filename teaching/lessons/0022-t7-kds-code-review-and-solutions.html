T7 KDS Code Review: Findings, Domain Impact & Solutions

Lesson 0022 · Sembilu Operating System · Informed Knowledge & Context

In this lesson, we review the code review findings from T7 (Kitchen Display System & Staff Order Management), connecting each technical issue directly to real-world kitchen operations and seeing how our solutions fixed them!

🔍 1. Code Review Findings & Operational Solutions

Finding 1: Missing Today's Date Filter on KDS Screen

What was happening: GET /api/staff/orders fetched all orders in history for a branch.

Real-World Impact: Chef Budi's kitchen screen would be cluttered with old orders from last month alongside today's active table orders!

The Solution: Added Knex date filtering: .whereRaw("DATE(orders.created_at) = CURRENT_DATE").

Finding 2: Silent Fallback on Cross-Branch Query Attempts

What was happening: If a waiter at Tegal passed ?branch_id=2 (Slawi), the server silently returned Tegal orders.

Real-World Impact: The waiter's tablet would display Tegal orders thinking it was looking at Slawi, causing confusion.

The Solution: Added an explicit check returning HTTP 403 Forbidden if a non-manager staff member queries another branch.

Finding 3: Item Status & Order Status Boundary Confusion

What was happening: Checked item.status === "served" when testing if all dishes were done.

Real-World Impact: Mixed up dish preparation states (kitchen) with table delivery states (waiter floor).

The Solution: Restricted item status checking strictly to item.status === "done".

Finding 4: Overly Permissive Table Status Endpoint

What was happening: Allowed staff to set order status to pending or cooking via PATCH /api/staff/orders/:id.

Real-World Impact: A staff member could accidentally revert a completed table back to pending.

The Solution: Restricted order status updates strictly to ["served", "paid"].

📚 2. Beginner's Code Glossary

whereRaw()
A Knex method allowing raw SQL expressions (like PostgreSQL's CURRENT_DATE) in queries.
CURRENT_DATE
PostgreSQL keyword representing today's calendar date.
checkBranchAccess()
Our helper function verifying whether a staff member has permission to view or edit data at a specific branch.
403 Forbidden
HTTP status code returned when a user is authenticated but lacks permission for the target resource.

1. Today's Date Filter & Branch Security Check

if (req.query.branch_id && staff.role !== "manager" && Number(req.query.branch_id) !== staff.branch_id) {
  res.status(403).json({ error: "Forbidden: Cannot access orders belonging to another branch." })
  return
}

const orders = await db("orders")
  .where({ branch_id: branchId })
  .whereRaw("DATE(orders.created_at) = CURRENT_DATE")
  .orderBy("created_at", "desc")
Explanation:
  • staff.role !== "manager" && Number(req.query.branch_id) !== staff.branch_id: If a waiter tries to pass a different branch ID, fail immediately with HTTP 403!
  • whereRaw("DATE(orders.created_at) = CURRENT_DATE"): Filters SQL query results to strictly today's orders.

2. Restricted Order Status Updates

const ALLOWED_STAFF_ORDER_UPDATES = ["served", "paid"] as const

if (!newStatus || !ALLOWED_STAFF_ORDER_UPDATES.includes(newStatus as AllowedOrderUpdate)) {
  res.status(400).json({ error: "Invalid order status value. Allowed status updates: 'served', 'paid'." })
  return
}
Explanation:
  • ALLOWED_STAFF_ORDER_UPDATES: Locks the endpoint so waiters can only mark orders as served or paid.
