T7 KDS: Initial Implementation, Code Review & Final Refactor

Lesson 0022 · Sembilu Operating System · Informed Knowledge & Context

In this lesson, we trace the full lifecycle of T7 (Kitchen Display System & Staff Order Management) — starting from our initial implementation, through our dual-axis code review findings, to our final refactored solution!

🚀 1. Initial Implementation Report (Before Code Review)

Our initial build established the core API routes needed for kitchen and floor staff in server/routes/staff-orders.ts:

  • GET /api/staff/orders: Fetched orders matching the staff member's branch_id, joining dish and sambal details for each order item.
  • PATCH /api/staff/orders/:id/items/:itemId: Updated item status following a forward state machine (pending ➔ cooking ➔ done) and automatically updated parent order status to cooking when the first dish started.
  • PATCH /api/staff/orders/:id: Updated table order status.

🔍 2. Dual-Axis Code Review Findings

Spec Finding Missing Today's Date Filter

Observed Code: GET /api/staff/orders ran db("orders").where({ branch_id }) without filtering by creation date.

Kitchen Impact: Chef Budi's display screen would be cluttered with old historical orders from last month alongside active orders from today!

Security Finding Silent Fallback on Cross-Branch Queries

Observed Code: Non-manager staff passing ?branch_id=2 silently fell back to their token branch (branch_id: 1).

Staff Impact: Waiter Wati's tablet would display Tegal orders thinking it succeeded in querying Slawi. Security boundaries must fail fast with HTTP 403 Forbidden!

Domain Finding Item vs. Order Status Boundary Confusion

Observed Code: Checked item.status === "done" || item.status === "served".

Domain Impact: served is a table-level delivery state (waiter floor), whereas kitchen items are strictly pending ➔ cooking ➔ done.

Spec Finding Overly Permissive Order Status Modifications

Observed Code: PATCH /api/staff/orders/:id accepted all 6 order statuses, including pending and cooking.

Floor Impact: Staff could accidentally revert a completed table order back to pending, bypassing kitchen workflows.

🛠️ 3. Final Refactored Solution & Code Walkthrough

whereRaw()
Knex method for running raw SQL date functions (e.g. DATE(orders.created_at) = CURRENT_DATE).
checkBranchAccess()
Security helper validating whether staff role/branch matches the target branch before database queries execute.
403 Forbidden
HTTP status code returned when authenticated staff attempt to access unauthorized branch data.

1. Today's Date Filter & Explicit 403 Guard

// 1. Explicit 403 check for unauthorized cross-branch queries
if (req.query.branch_id && staff.role !== "manager" && Number(req.query.branch_id) !== staff.branch_id) {
  res.status(403).json({ error: "Forbidden: Cannot access orders belonging to another branch." })
  return
}

// 2. Fetch today's orders only using CURRENT_DATE
const orders = await db("orders")
  .where({ branch_id: branchId })
  .whereRaw("DATE(orders.created_at) = CURRENT_DATE")
  .orderBy("created_at", "desc")
How this connects context to code:
  • whereRaw("DATE(orders.created_at) = CURRENT_DATE") keeps the KDS screen 100% focused on active orders placed today.
  • Fails fast with HTTP 403 if non-manager waiters attempt cross-branch queries.

2. Restricted Order Status Updates (Served & Paid Only)

const ALLOWED_STAFF_ORDER_UPDATES = ["served", "paid"] as const

if (!newStatus || !ALLOWED_STAFF_ORDER_UPDATES.includes(newStatus as AllowedOrderUpdate)) {
  res.status(400).json({ error: "Invalid order status value. Allowed status updates: 'served', 'paid'." })
  return
}
How this connects context to code:
  • Locks PATCH /api/staff/orders/:id so floor waiters can only mark tables as served or paid.
