T4 Recap: The Ordering Flow

Lesson 14 · The biggest ticket yet — a 4-step page from identity to confirmation.

👩‍🍳 Wati now takes orders at the table. Before T4, customers would wave at Wati and say "Ikan Bakar, please." After T4, they scan the QR code on their table, tap through 4 steps on their phone, and the order appears in the system. Wati just brings the food.

T4 is the biggest ticket so far because it's the first one that handles a multi-step user flow — not just a single API call, but a complete journey from "who are you?" to "your order is in!"

The 4 steps

StepWhat happensData collected
1. Identity Customer enters name + phone Who is ordering? Links to T3's customer table
2. Menu Customer browses dishes, adds quantities What do they want? Ikan Bakar × 2, Gurame × 1
3. Sambal Per dish, pick a free sambal. Extra costs money. Ikan Bakar → Sambal Terasi (free), Gurame → no sambal
4. Review See the total, confirm, submit Order sent to the kitchen!

The new tables

orders                                order_items
┌──────────────────────────┐          ┌──────────────────────────┐
│ id                       │          │ id                       │
│ branch_id                │◄─────────│ order_id (FK)            │
│ customer_id (FK)         │          │ dish_id (FK)             │
│ table_number             │          │ quantity                 │
│ status: pending → paid   │          │ sambal_id (FK, nullable) │

│ created_at               │          │ notes                    │
└──────────────────────────┘          └──────────────────────────┘

Why two tables instead of one? Same reason as T3 — one order can have many items. An order with 3 items stores the order once and the items separately. This is called a one-to-many relationship.

Step 3 is the interesting one. When you order Ikan Bakar at SEMBILU Jakarta (branch 4), the server checks: "Does Ikan Bakar exist at branch 4?" If not, it rejects the order. This prevents someone from ordering a dish that isn't available at their branch.

The sambal pricing logic

This was the trickiest part of T4. Here's how it works:

// You ordered:
//   Ikan Bakar × 2  →  free sambal allocation: 2
//   Gurame × 1      →  free sambal allocation: 1
//   Total free: 3

if (used_sambals <= free_sambals) {
  // all free, no extra charge
} else {
  // extra sambals cost money
  total += extra_sambal_count × sambal_price
}

Each sambal now has a price (added in a separate migration before T4). Sambal Terasi: Rp 7.000. Sambal Tomat: Rp 5.000. Sambal Ikan Asin: Rp 10.000. These prices were added to the existing sambals table — no new table needed.

The code review bug

During the code review, a bug was found:

Before fix: The system counted "how many items have a sambal?" instead of "how many portions have a sambal?" If you ordered Ikan Bakar × 2 with sambal, it counted as 1 used sambal instead of 2.

After fix: The count multiplies by quantity: usedSambalCount = cart.reduce((s, c) => s + (c.sambalId ? c.quantity : 0), 0)

This is a classic bug: counting items vs counting quantities. Easy to miss, easy to fix.
