PostgreSQL: The Restaurant Ledger

Lesson 3 · Why a relational database fits Sembilu like a ledger fits a restaurant.

📖 Imagine a restaurant's paper ledger. Every restaurant has one — a thick book where the waiter writes the order, the chef ticks off dishes as they're cooked, and the cashier tallies the bill at the end. Orders link to tables, tables sit in branches, each order has multiple items. Everything relates to everything else.

That's what a relational database is — a digital version of that ledger. PostgreSQL is simply the most respected one: open-source, battle-tested, and used by companies of every size.

Tables: The chapters of the ledger

A restaurant ledger has sections: one page for orders, another for menu items, another for customers. In PostgreSQL, those sections are called tables.

Let's look at Sembilu's actual data from src/data.ts and see how it becomes tables:

Primary keys: The ID card

Every branch, every dish, every order needs a unique identifier — like how every order in a restaurant has an order number. That's a primary key.

In Sembilu's data.ts, each location has a unique number:

locations = [
  { no: "꧑", city: "Tegal",    address: "Jl. Jenderal Sudirman No. 17" },
  { no: "꧒", city: "Slawi",    address: "Jl. Raya Slawi No. 9" },
  { no: "꧓", city: "Semarang", address: "Jl. Pandanaran No. 24" },
  { no: "꧔", city: "Jakarta",  address: "Jl. Senopati No. 88" },
]

That no field (꧑, ꧒, ꧓, ꧔) is a primary key in disguise — it uniquely identifies each branch. In PostgreSQL, we'd write this: 

CREATE TABLE branches (
  id      SERIAL PRIMARY KEY,  -- auto-incrementing number
  city    VARCHAR(100) NOT NULL,
  address TEXT NOT NULL,
  hours   VARCHAR(100),
  open    BOOLEAN DEFAULT true
);

Foreign keys: The thread connecting tables

Here's where the "relational" part comes in. A dish doesn't exist in a vacuum — it's served at a specific branch. In the mockup, the Ikan Bakar Pantura exists only in the data file. But in a real system, we need to know: which branch serves it?

A foreign key is a column in one table that points to the primary key of another. It's like writing "See page 12" in a notebook. 

CREATE TABLE dishes (
  id          SERIAL PRIMARY KEY,
  name        VARCHAR(100) NOT NULL,
  description TEXT,
  price       INTEGER NOT NULL,
  branch_id   INTEGER REFERENCES branches(id)  -- ← foreign key
);

This says: "Every dish belongs to a branch. And you can't create a dish for a branch that doesn't exist." PostgreSQL enforces this — no orphan data allowed.

Why this matters for Sembilu: When a waiter submits an order for "Ikan Bakar Pantura" at the Tegal branch, the database confirms: "Yes, that dish exists at that branch." And the order is linked to the branch, so the kitchen in Tegal sees it — not the kitchen in Jakarta. The foreign key prevents mistakes your code would otherwise have to catch manually.

Why PostgreSQL, concretely

Here's how PostgreSQL maps to Sembilu's needs:

Sembilu needs to…PostgreSQL feature
Know which dishes belong to which branchForeign key → you can't assign a dish to a branch that doesn't exist
List all orders at a branch todaySELECT * FROM orders WHERE branch_id = 1 AND date = TODAY
Prevent double-booking a tableUnique constraint on (branch_id, table_number, time_slot)
Find what's cooking in the kitchen right nowSELECT * FROM order_items WHERE status = 'cooking'
Calculate tonight's revenueSELECT SUM(price) FROM orders WHERE date = TODAY
Customer tracks their order liveThey just query the same orders table — the status field is shared

The key insight

This last row is the whole point of building this project as one system:

Customer tracks order → reads orders.status.
Kitchen marks "done" → writes order_items.status = 'done'.
Waiter sees it → reads the same field.

One database. Everyone reads and writes the same source of truth. No syncing. No "the customer sees something different from the kitchen." That's what a relational database gives you — a single, consistent ledger that everyone works from.
